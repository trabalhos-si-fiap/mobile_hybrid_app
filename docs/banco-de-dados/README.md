# Banco de dados: MER, DER e PL/SQL

Insumos para montar o modelo de dados da entrega da Fase 6. O diagrama é
montado numa ferramenta (SQL Developer Data Modeler para o DER, brModelo
para o MER), a partir dos arquivos desta pasta. A fonte da verdade continua
sendo o Flyway (`api/src/main/resources/db/`).

| Arquivo | Para quê |
|---|---|
| [`ddl-consolidado.sql`](./ddl-consolidado.sql) | As 19 tabelas, 27 FKs e 29 índices num arquivo só, para importar no Data Modeler |
| [`conferir-ddl.sh`](./conferir-ddl.sh) | Prova, num Oracle efêmero, que o DDL consolidado gera o mesmo esquema que as migrations |
| [`mer-conceitual.md`](./mer-conceitual.md) | Entidades, relacionamentos e cardinalidades para o brModelo |
| [`dicionario-de-dados.md`](./dicionario-de-dados.md) | Cada tabela e coluna: tipo, nulidade, padrão, chave, valores aceitos e índices |
| [`plsql.md`](./plsql.md) | Os 7 objetos PL/SQL: assinatura, regra, tabelas, erros, quem chama e testes |

## DER no SQL Developer Data Modeler

1. File > Import > DDL File e escolha `ddl-consolidado.sql`.
2. Banco: Oracle Database 23ai (ou a versão mais nova que a ferramenta
   oferecer). Confirme a importação no relatório que o Data Modeler mostra.
3. Confira o resultado: 19 tabelas no modelo relacional e 27 linhas de FK.
4. Crie três subviews (botão direito no modelo relacional > New SubView) e
   arraste as tabelas:
   - **Atendimento omnichannel:** `admin_users`, `skills`, `employees`,
     `employee_skills`, `ticket_tipo_config`, `tickets`, `ticket_messages`,
     `ticket_attachments`, `ticket_events` e `notifications`;
   - **Chatbot:** `chatbot_faq`, `chatbot_faq_keywords`,
     `chatbot_conversations` e `chatbot_messages`, mais `admin_users`,
     `ticket_tipo_config` e `tickets` como contexto;
   - **Edu Admin:** `products`, `inventories`, `inventory_adjustments`,
     `carriers` e `carrier_occurrences`.
5. Opcional: botão "Engineer to Logical Model" (`<<`) da barra de
   ferramentas, para ter também o modelo lógico (notação Barker ou Bachman).
6. Exporte cada subview como imagem (File > Print Diagram > To Image File)
   ou PDF.

## Plano B: importar do Oracle de pé

Se o importador de DDL recusar alguma sintaxe (o `BOOLEAN` nativo do 23ai e
o `GENERATED BY DEFAULT ON NULL AS IDENTITY` são os candidatos em versões
antigas da ferramenta), importe direto do banco:

1. Suba a stack (`docker compose up -d` em `api/`). A API aplica as
   migrations ao subir; o banco precisa estar com a `V8`. Confira com
   `SELECT MAX(TO_NUMBER("version")) FROM "flyway_schema_history";`, que
   deve dar 9 ou mais (a `V9` é seed).
2. No Data Modeler: File > Import > Data Dictionary, nova conexão:
   - host `localhost`, porta `1521`, serviço `FREEPDB1`;
   - usuário `edu_admin`, senha `edu_admin` (padrões do
     `api/docker-compose.yml`; valem os valores de `DB_USERNAME`,
     `DB_PASSWORD` e `ORACLE_PORT` se você os mudou no `.env`).
3. Escolha o schema `EDU_ADMIN`, marque todas as tabelas, exceto
   `flyway_schema_history`, e siga do passo 3 da seção anterior.

Se nem assim a ferramenta aceitar o `BOOLEAN`, troque o tipo das 4 colunas
`BOOLEAN` (`products.active`, `ticket_tipo_config.active`,
`tickets.engineering_alert` e `chatbot_faq.active`) por `NUMBER(1)` só no
modelo da ferramenta, e anote isso na legenda do diagrama.

## MER no brModelo

1. Novo modelo conceitual.
2. Crie as entidades da seção "Entidades" do
   [`mer-conceitual.md`](./mer-conceitual.md), com o identificador marcado
   e os atributos listados. Use os três grupos (atendimento, chatbot e Edu
   Admin) como regiões do desenho.
3. Crie a especialização de Usuário em Atendente (parcial) e o atributo
   multivalorado composto "palavras-chave" (palavra e peso) em Pergunta do FAQ.
4. Crie os 24 relacionamentos da tabela "Relacionamentos". A cardinalidade
   da coluna "Junto de A" vai junto da entidade A, e a de "Junto de B" junto
   da entidade B. Na convenção do brModelo, o número junto de uma entidade
   diz quantas ocorrências dela se ligam a uma ocorrência da outra: em
   Usuário (1,1) — abre — (0,N) Ticket, cada ticket tem 1 usuário.
5. Confira contra a coluna "Leitura" de cada linha.

## Correspondência com a FIAP

O enunciado (`Omnichannel Edu.txt`) sugere 5 tabelas, pensadas para
PostgreSQL. O projeto usa Oracle (exigência da Fase 6) e cobre as 5 com
nomes do domínio:

| Sugestão da FIAP | Tabela real | Diferença |
|---|---|---|
| `Occurrence` (ID, User_ID, Segment, Description, Status, Created_At) | `tickets` | Mesmos campos (`id`, `user_id`, `segment`, `description`, `status`, `created_at`), com o segmento como FK para `ticket_tipo_config`. Acrescenta canal, prioridade, atendente responsável, prazos de SLA, alerta de engenharia e as datas de cada etapa. |
| `Occurrence_Attachment` (ID, Occurrence_ID, File_URL) | `ticket_attachments` | Em vez da URL, guarda a chave do objeto no MinIO (`object_key`); o arquivo é servido por `GET /api/v1/tickets/{ticketId}/attachments/{attachmentId}`. Acrescenta nome, tipo, tamanho, quem enviou e a mensagem a que o anexo pertence. |
| `Skill` (ID, Name) | `skills` | Acrescenta o código (`code`), que a API usa para achar os desenvolvedores do alerta de engenharia. |
| `Employee_Skill` | `employee_skills` | Igual, mas liga `employees` (o atendente), e não o usuário. |
| `Occurrence_Message` (ID, Occurrence_ID, Sender_Type, Message_Body, Timestamp) | `ticket_messages` | Mesmos campos (`id`, `ticket_id`, `sender_type`, `body`, `created_at`), mais o autor (`sender_user_id`) e o tipo `SYSTEM` para avisos automáticos. |

Tabelas que não estavam na sugestão:

- `ticket_tipo_config`: a matriz de triagem (segmento → skill → fila →
  prioridade → SLA) num lugar que o PL/SQL consulta, em vez de fixa no
  código.
- `employees`: presença (`ONLINE`, `AUSENTE`, `OFFLINE`) e carga de cada
  atendente, que o roteamento usa; separa o atendente do usuário.
- `ticket_events`: a trilha de cada ticket (roteado, assumido, transferido,
  escalado...). Base do histórico no console e do dashboard.
- `notifications`: avisos para o app e o console, lidos por polling.
- `chatbot_faq`, `chatbot_faq_keywords`, `chatbot_conversations` e
  `chatbot_messages`: o chatbot nível 0 e a conversa que o atendente vê no
  console.
- `products`, `inventories`, `inventory_adjustments`, `carriers` e
  `carrier_occurrences`: o Edu Admin anterior à Fase 6, mantido.

## Manutenção

Quem criar uma migration nova (a próxima é a `V10`):

1. Acrescente a mudança ao `ddl-consolidado.sql`, no bloco da tabela.
2. Rode `docs/banco-de-dados/conferir-ddl.sh` (só precisa de Docker; leva
   cerca de 20 s e não mexe na stack). Ele lê todas as migrations da pasta,
   então falha até o DDL ser atualizado.
3. Revise o dicionário, o MER e, se mudou PL/SQL, o `plsql.md`.
